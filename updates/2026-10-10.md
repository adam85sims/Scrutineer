# Update — 2026-10-10

## Headline

Fixed the front door: `pip install scrutineer-agents` followed by the README's Quick Start now
works. Both 0.3.0 publish-verification defects are closed, and the `.[dev]`-only failures with
them.

## What changed

- **`examples/` ships inside the wheel.** `[tool.hatch.build.targets.wheel.force-include]` maps
  the repo's `examples/` to `scrutineer/examples/` (26 files). `examples/` stays the single
  source of truth; there is no second copy to drift.
- **`scrutineer init`** writes the starter kit into `<dir>/scrutineer-examples/` (default
  `./`), prints the commands to run, and refuses to overwrite without `--force`. It resolves
  the kit from the installed package, falling back to the repo root for editable installs.
- **PyYAML is a core dependency** (`click` + `pyyaml`). It was in `[governance]`, so a plain
  install could not run a single shipped scenario. `[governance]` remains as a resolving alias.
- **The YAML loader raises `ScenarioLoadError`** instead of returning `[]` after printing the
  real reason. `run` catches it, prints one true error, exits 1.
- **README Quick Start rewritten** around commands that exist for a pip user, plus a new
  `scrutineer init` line in the CLI list. The OpenAI adapter snippet now imports
  `wrap_openai_agent` (it had named a function that does not exist).
- **`docs/QUICKSTART.md`** no longer says the release is pending, no longer installs from a git
  URL while 0.3.0 is on PyPI, and no longer points at `scenarios/basic.yaml`.
- **`examples/README.md` rewritten.** It documented another project's CLI (`agent-fw-setup`) and
  would now travel inside the wheel as part of the starter kit.
- 8 tests in `tests/scrutineer/test_cli_init.py`.

# Update — 2026-10-10 (afternoon, autonomous)

## Headline

Hunted the same "it lies" defect class further down the same path: into the file that ships
*before* the README, the entry point that crashes instead of explaining, and the command that
said "no scenarios" over twelve of them.

## What changed

- **`src/scrutineer/README.md` repaired.** It ships inside the wheel, so it is the first thing a
  user who opens the installed package reads — and it opened with
  `pip install agent-frameworks[scrutineer]`, a distribution that 404s on PyPI. Seven install
  lines corrected, the false "zero required dependencies" claim replaced with `click` + `pyyaml`,
  the CLI reference rebuilt from real `--help` output (missing `init`, `trace`, `serve`), four
  modules added to its architecture tree, and a working first-run snippet added.
- **`scrutineer-serve` no longer dies with a traceback.** `scrutineer/web/__init__.py` imported
  the FastAPI-backed app at package import, which runs before the entry point function, so a
  lean install got `ModuleNotFoundError: No module named 'fastapi'`. `create_app` resolves
  lazily now (PEP 562) and the command reports the missing extra, exit 1.
- **Two install hints named the wrong distribution** (`pip install scrutineer[web]` — the
  unrelated PyPI project). Both corrected, including `src/scrutineer/web/README.md`, which ships
  in the wheel.
- **`scrutineer list` / `run --all` discover scenario files.** `./scenarios/` and
  `./scrutineer-examples/` are scanned; a file counts only if shaped like a scenario, because the
  kit ships config templates in the same trees. `init → list → run --all` is a closed loop.
- **`run --path <config file>`** used to execute a governance template as a scenario called
  "unnamed" and report a failure for a scenario nobody wrote. Now: "No scenarios found in file."
- **`examples/e2e-scenario-saved.yaml` removed and gitignored.** A playwright byproduct committed
  in `cd25c02`; it shipped in the starter kit and `run --all` reported it as a failure.
- **`docs/CHAOS_BENCHMARK.md` rewritten.** It shipped in the sdist while presenting invented
  numbers as production evidence — "PagerDuty: 28% of incidents", "Microservices: 60% of outages
  cascade" — with fidelity verdicts like "matches reality" beside them and a "Correlation
  Evidence" section asserting a distribution that was never measured. Every figure is **removed
  rather than restated**: deleting the number while leaving the verdict would be the worse
  half-fix, because the missing number is visible and the verdict is not. Rows now describe only
  what the code does, and the fidelity column reads "benchmarked against production data: No" for
  all fifteen. Added what a real benchmark would require, and a table of which injectors can be
  used from a scenario file (four can; three are refused on purpose).
- A Hermes skill, `shipped-artifact-verification`, capturing the method as a reusable procedure.

## Verified

- 665 tests pass serially **and** under `-n auto -p randomly`; `ruff check src/ tests/` clean.
- Lean install (wheel, no extras): `scrutineer-serve --port N` → one error line naming the
  `web` extra, exit 1 — no traceback. Same for `scrutineer serve`.
- Full install (wheel + `[web]`): `create_app()` builds a FastAPI app via the lazy export, and
  the entry point is importable.
- Fresh cwd: `init` → 25 files; `list` → 12 scenarios (config templates correctly ignored);
  `run --all` → 11 passed, 1 failed (the intentional negative control); a malformed file in
  `scenarios/` → one clean error, exit 1, zero tracebacks.

## Found while doing it

- **The starter kit made a bad first impression**: `run --all` right after `init` reported two
  failures — one deliberate, one a committed test artifact. A user cannot tell those apart.
- **Edge case, not a crash:** `run --all` exits 1 because the shipped negative control fails by
  design. Arguably right (the tool must be able to say no) but it is worth a line in the docs so
  a first-time user is not surprised.
- **The WebUI saves scenarios into `examples/`** (`--scenario-dir` defaults there), i.e. into the
  repository's own tree. That is the mechanism that produced the committed artifact. Left alone:
  changing the storage contract would break the e2e tests' assertions.
- Three adversarial subagent reviews were run against the day's work; the one covering the new
  skill found eight defects in it by executing it, including one stale-`dist/` contradiction and
  a missing entry-point check that uncovered the `scrutineer-serve` crash above.
- **The discovery change was rejected by review and redesigned.** The reviewer ran the real
  commands and returned *unsound*: it raised for files it could not even classify, so one
  unrelated multi-document YAML manifest — or an editor's read-only lock file — made `list`,
  `run --all`, `run --scenario <a good one>` and `info` all exit 1. That is a worse failure than
  the bug it fixed. The same review showed the gate accepted and then **executed** a
  docker-compose file, a `package.json`, a GitHub workflow, an Ansible playbook, a Grafana
  dashboard and a Taskfile as six failing scenarios, and that `allow_no_assertions: true` alone
  was a false negative. The redesign: multi-document YAML parses as multiple scenarios; the gate
  demands *identifiable* AND *substantive*; unreadable or unclassifiable files are warnings, never
  fatal, with `run --all` exiting 1 on "this run is incomplete"; `os.walk(onerror=...)` reports a
  permission-denied subdirectory instead of dropping the subtree. Every one of the reviewer's cases
  was then re-run at the shell and shown fixed, and a further gap it had not found — zero
  discoverable scenarios *plus* an unreadable file exited 0 — was caught and pinned.
  Lesson for the log: **a fix that fails loudly on input it cannot classify has only moved the
  silent failure into a hard one.** Reserve the raise for what you have *proved* is a scenario.
- **A second review round rejected parts of the redesign too** (`sound-with-fixes`, five more
  defects). The sharpest: the gate was applied per *file* while the builder works per *document*,
  so a config document sharing a file with a real scenario was still built and executed as
  "unnamed" — the same defect class, made easier to hit by the multi-document support added in the
  same change. Also: requiring an `id`/`name` was stricter than `_build_scenarios`, which silently
  dropped a valid `task` + `assertions` scenario *and* reported it as lacking those very keys; and
  the `_SCENARIO_IGNORED_DIRS` pruning I had added for scan cost hid a scenario sitting in a
  directory named `build/`. The prune list is now `__pycache__` and hidden trees only, the gate is
  per document with a two-block rule, and `run --all --json-output` carries `"incomplete": true`.
  Note for the log: **check every error-bearing path is reachable before writing tests for it** —
  per-item filtering made a `ValueError` branch dead, so the branch and its test were both deleted
  rather than left as decoration.
- **The T2 verification went round twice as well, and the second round found a bug the README was
  hiding.** Fixing the doc's unimported snippet names was straightforward; checking them by
  *execution* revealed that the documented JSON workflow had never worked. `--json-output` was
  advertised as machine-readable while writing its progress lines to stdout, so
  `> results.json` produced garbage — and once stdout was pure, `baseline record --path
  results.json` raised `KeyError: 'assertion_name'`, because the emitter writes `name`/`error`
  and the deserializer wanted `assertion_name`/`error_message`. A recorded baseline was therefore
  also silently losing every failure *reason*, which is the worse half: the numbers still looked
  right. Both fixed, with `tests/scrutineer/test_json_roundtrip.py` running the two documented
  commands in order — the only order in which either defect is visible.
- While verifying that, found and logged (not fixed): **`baseline record` writes baselines into
  the Python environment, not the user's project** — `get_baseline_dir()` resolves the project
  root from `__file__`, which is `lib/python3.11/` for an installed wheel. Proven on a clean
  install: the baseline landed in `<venv>/lib/python3.11/.scrutineer/baselines/`. Where a tool
  stores a user's data is a product decision, so it is Adam's call.
- **The T4 rewrite was also caught overstating, in the very direction it was written to correct.**
  Its provenance note said the removed figures had "no citation, date or report name" — but the
  old table did carry a company label per row (PagerDuty, AWS, OpenAI, "Microservices"); what was
  missing was a report name, a date and any link. A note complaining about loose provenance has to
  be exact about what was actually missing, or it commits the same sin. Also corrected: the doc
  cited `scrutineer/chaos.py` when the tree is src-layout (`src/scrutineer/chaos.py`), and
  attributed one shared `on_step`/`on_failure` hook to three injectors that each use a different
  one (`ContextDegradation.on_step`, `CascadingFailures.on_failure`, `SpecDrift.check_step`).
  Every remaining path and symbol in the document was then checked against the tree.
- **A third review round on the discovery work found the failure mode that matters most for a test
  tool: a false red.** All six round-3 fixes held, and seven new defects were found — two of them
  making `run --all` exit 1 on a *correct* tree. An Emacs lock file (`scenarios/.#demo.yaml`, a
  dangling symlink whose name ends in `.yaml`) was read as an unreadable scenario, so a run in
  which every scenario passed reported itself incomplete; and a symlinked directory of ordinary
  configs (`settings.json`, a workspace `package.json`) was announced as "holds scenario files" on
  file suffix alone. Both fixed: candidates must now be real files, and a skipped directory is
  reported only if it actually holds something runnable. Also fixed: a virtualenv under
  `scenarios/` was walking the packages' own bundled YAML into the run (200 phantom scenarios from
  one `venv/`) — environment trees are now skipped and named; and duplicate scenario ids, and
  scenarios hidden in a dot-directory, are no longer dropped without a word.
  Two of my own tests caught a bug I had introduced minutes earlier: probing a directory for
  `pyvenv.cfg` raised `PermissionError` on an unreadable one, turning an environment check into the
  traceback it existed to prevent. The lesson repeats at every layer — **a check that runs while
  you are failing is itself a failure path, and needs the same care**.
- **A fourth round (the JSON/baseline batch) closed with three more fixes, one of them mine to
  own.** `--json-output --verbose` still leaked the verbose header to stdout: the same defect one
  flag-combination deeper, which no test exercised. `run --all --json-output` with nothing to run
  wrote an empty file rather than a document, so `> results.json` then died in `baseline record`.
  And `_discover_decorated_scenarios` guarded with `except Exception` while pytest's `Skipped`
  derives from `BaseException` — so a project whose test module `importorskip`s a missing optional
  dependency lost *every* scenario, which is also the intermittent skip my own new test triggered
  under `-n auto -p randomly`. All three fixed, with a test for the flag combination nothing had
  covered, and the suite re-run under the exact seed that reproduced the flake.
  The pattern across four rounds is worth keeping: **each fix was correct about the case it was
  written for and wrong about a neighbour** — per-file versus per-document, a raise for a file it
  could not classify, a suffix test where a content test was needed, a guard that was one
  exception class too narrow.
